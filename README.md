# Зміна — PWA + Firebase + GitHub Pages

Збережено **оригінальний дизайн і логіку**: календар 4/2, зарплата за 1–15 і 16–кінець місяця, виплати 25-го та 10-го наступного місяця, каса, місячний план продажів, премія 2 000 ₴ за виконання 100% плану з виплатою 15-го наступного місяця, журнал каси, реєстрація й адмінпанель.

## Що нового

- **PWA**: `manifest.webmanifest`, іконки і `sw.js`. На Android можна встановити «Зміну» через Chrome → «Встановити застосунок»/«Додати на головний екран». Відкриватиметься без адресного рядка як окремий застосунок.
- **Офлайн**: локальні файли кешуються service worker; Firestore налаштовано на постійний IndexedDB кеш, що дозволяє переглядати вже завантажені документи й чергувати локальні записи без мережі. Додатково зберігається власна локальна копія календаря для підстрахування. При поверненні інтернету Firebase підтверджує синхронізацію.
- **Автооновлення після кожного push**: `.github/workflows/deploy-pages.yml` сам публікує папку `public/`, генерує `version.json` із SHA коміту та підставляє номер версії в `sw.js`. Запущена PWA перевіряє новий реліз при відкритті/фокусі/відновленні мережі та кожні 5 хвилин, потім перезавантажує сторінку **лише коли немає незбережених/несинхронізованих змін**.
- **Дані з Firebase**, а не з версії сайту. Публікація нових файлів не видаляє облікові записи й записи у Firestore.

## 1. Налаштувати Firebase (як і в попередній версії)

1. Firebase Console → Project settings → Your apps: додайте вебзастосунок, скопіюйте `firebaseConfig`.
2. Authentication → Sign-in method: увімкніть Email/Password.
3. Firestore Database: створіть **Standard** базу `(default)`, бажано європейський регіон.
4. У `public/firebase-config.js` замініть приклад своїми `apiKey`, `authDomain`, `projectId`, `appId` тощо. `firebaseConfig` — публічна конфігурація, не приватний ключ.
5. Firestore Database → Rules: вставте вміст **`firestore.rules`** (файл знаходиться в корені архіву), натисніть Publish. У GitHub Pages ці правила самі по собі не розгортаються.
6. Authentication → Settings → Authorized domains: додайте **`ВАШ-ЛОГІН.github.io`** (без `https://` і шляху репозиторію). Кастомний домен додайте окремо.

**ВАЖЛИВО:** Firebase Service Account JSON, приватні ключі та паролі **не завантажуйте** до репозиторію або в `public/`.

## 2. Розмістити саме цю версію на GitHub Pages

> **Ця версія використовує GitHub Actions, а не `Deploy from a branch`.** Це потрібно для автоматичної зміни номера версії при кожному оновленні.

1. Створіть GitHub-репозиторій, наприклад `zmina`, з гілкою `main`.
2. У **корінь репозиторію** завантажте ВМІСТ папки `zmina-pwa` (не саму папку як вкладену): `public/`, `.github/workflows/deploy-pages.yml`, `firestore.rules`, `README.md`, `package.json` тощо. **Зверніть увагу: `.github` — прихована папка**, не втратьте її під час завантаження.
3. Якщо раніше ви заливали `index.html`, `app.js`, `styles.css` безпосередньо в корінь репозиторію, перенесіть їх у папку `public/` або замініть структурою з цього архіву. Не залишайте дві копії сайту в різних місцях.
4. GitHub → репозиторій → **Settings → Pages → Build and deployment → Source: `GitHub Actions`** (не `Deploy from a branch`).
5. У **Actions** побачите запуск `Publish Zmina PWA to GitHub Pages`. Якщо GitHub попросить дозволити Actions, дозвольте workflow. Після успішної публікації сайт буде за адресою `https://ВАШ-ЛОГІН.github.io/zmina/`.
6. Для майбутніх змін редагуйте файли **всередині `public/`**. Кожен push у `main` автоматично запустить публікацію і змінить версію додатку. **Не потрібно вручну міняти `sw.js` або `version.json`.**

Якщо GitHub Pages вже працює через `Deploy from a branch`, **переключіть Source на `GitHub Actions`** до першого оновлення PWA, інакше автоматичний механізм версій не запуститься.

## 3. Встановити на Android / комп’ютері

1. На телефоні відкрийте GitHub Pages URL у Chrome **з інтернетом** і увійдіть у свій Firebase-акаунт.
2. Меню Chrome (⋮) → **Встановити застосунок** або **Додати на головний екран**. Поява пункту залежить від версії браузера.
3. Запустіть «Зміну» з домашнього екрана. Дайте завершитися першому завантаженню та синхронізації; для надійного кешування Firebase SDK після першого встановлення повторно відкрийте застосунок онлайн.
4. Перевірте офлайн: увімкніть режим польоту й знову відкрийте застосунок. Ви повинні бачити раніше завантажений календар. Додайте пробний запис; статус повідомить про очікування синхронізації. Вимкніть режим польоту, дочекайтеся напису «Збережено у Firebase», перезавантажте й перевірте запис.

Перший вхід/створення нового акаунта вимагає інтернету. Офлайн можна працювати тільки з акаунтом і даними, які **раніше були завантажені на пристрій**. Firebase JS модулі також повинні встигнути кешуватися. На деяких браузерах чи в приватному режимі постійний кеш недоступний.

## 4. Як працює автоматичне оновлення

- Після публікації на GitHub Actions створюється `version.json` з унікальним SHA коміту.
- У відкритому застосунку версія перевіряється кожні **5 хвилин**, а також під час відкриття, повернення до вікна та після відновлення інтернету.
- Якщо з’явилася нова версія, застосунок готує файли і сам активує її. Якщо користувач зараз вводить незбережені дані або має офлайн-зміни, оновлення відкладено.
- Якщо телефон офлайн, нова версія не може завантажитися. Вона буде отримана після появи зв’язку, коли браузер дозволить роботу/пробудження PWA. Закритий застосунок не отримує оновлення у фоновому режимі за гарантованим графіком.
- Важливо: оновлюються **файли програми**, не змінюються дані в Firebase.

## 5. Адмінпанель

Незмінно працює захищена роль `admin=true` з Firebase Custom Claims. Створити адміністратора можна скриптом `tools/grant-admin.mjs` на довіреному комп’ютері:

```bash
npm install
# Перед цим задайте GOOGLE_APPLICATION_CREDENTIALS, вказавши приватний JSON ПІЗА репозиторієм
npm run grant-admin -- admin@example.com
```

Після призначення права вийдіть і зайдіть повторно. Жодний приватний JSON не розміщуйте на GitHub.

## 6. Обмеження й захист даних

- Firestore зберігає **весь календар одним документом** `users/{uid}/data/calendar`. При одночасному редагуванні з двох пристроїв можливий конфлікт (Firebase використовує модель *last write wins*). Під час тривалого офлайн-редагування **не змінюйте той самий акаунт на іншому пристрої**. Сайт не має повноцінного злиття записів по днях. Рекомендується регулярний експорт JSON.
- Дані Firestore кешуються в IndexedDB, а підстрахувальна копія — в `localStorage` цього браузера. Використовуйте PWA **тільки на особистому довіреному пристрої**: браузер може зберігати зарплатні дані локально навіть після виходу. Очищення даних сайту/браузера видаляє несинхронізовані офлайн-записи; синхронізовані записи залишаються у Firebase.
- Дозвіл на доступ до чужих даних забезпечують `firestore.rules` та server-side Custom Claims, не перевірка в браузері.
- Не видаляйте `firebase-config.js`, `sw.js`, `manifest.webmanifest`, `pwa.js`, `version.json` із `public/`: це файли, необхідні для PWA.
- Реальну синхронізацію з Firebase не можна підтвердити без ваших налаштувань проєкту й облікового запису. Після публікації виконайте тест «офлайн → запис → онлайн → інший пристрій».

## Технічна структура

```text
zmina-pwa/
├── public/
│   ├── index.html, auth.html, admin.html
│   ├── app.js, cloud.js, auth.js, admin.js, logic.js
│   ├── styles.css, firebase-config.js
│   ├── manifest.webmanifest, sw.js, pwa.js, version.json
│   ├── icons/
│   └── favicon.svg
├── .github/workflows/deploy-pages.yml
├── firestore.rules
├── tools/grant-admin.mjs
├── tests/
└── README.md
```

Для локальної перевірки потрібен HTTP-сервер (`python -m http.server 8000 --directory public`); через `file://` PWA не працює. Локальний запуск має бути з localhost або HTTPS. Firebase Web SDK завантажується з офіційного CDN; для першого запуску потрібен інтернет.
